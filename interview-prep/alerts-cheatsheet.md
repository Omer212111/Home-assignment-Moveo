# מנגנון ההתראות: דף סיכום לראיון

## 0. המשפט הפותח (לשנן)
> "יש שני סוגי התראות: **monthly outlook** מתוזמן, שבוע לפני כל חודש, ו-**score change** שמופעל כש-scoring run חדש הופך לפעיל. כל התראה **נוצרת פעם אחת בדיוק** בזכות מפתח ייחודי ב-DB, ו**נשלחת לפחות פעם אחת** דרך outbox עם lease וניסיונות חוזרים. היא נשלחת ב-webhook בפורמט של Slack, ותמיד מוצגת גם ב-`GET /alerts` ובדף."

## 1. שני סוגי ההתראות

| | Monthly outlook | Score change |
|---|---|---|
| שאלה | אילו hubs נכנסים לחודש שהיה קשה להם היסטורית? | האם הסיכון של hub השתנה משמעותית? |
| טריגר | **זמן**: 7 ימים לפני תחילת החודש | **אירוע**: run חדש הופך לפעיל |
| חוק | index חודשי ≥ **300** **וגם** ≥ **3** אירועי עבר באותו חודש | שינוי index ≥ **25** נקודות **או** מעבר tier, בסך הכול ולכל hazard |
| Dedup key | `outlook:2027-01` | `change:3->4` |
| צורה | **digest אחד** לחודש, מהגרוע לפחות גרוע | הודעה אחת לכל run חדש |
| קוד | `check_outlook()` | `record_change_alert()` ו-`score_changes()` |

**הנימוקים למספרים:**
- **300** פירושו פי 3 מחודש ממוצע של hub טיפוסי, כלומר בערך 1.2 ימי הפרעה צפויים בחודש. עם סף 200 היו **109** התראות hub-חודש בשנה (alert fatigue). עם 300 יש כ-**60**: ינואר 17, פברואר 21, ומעט בקיץ.
- **≥ 3 אירועים** מסנן חודש שנראה קיצוני בגלל אירוע בודד (ספטמבר בנאשוויל: שיטפון אחד).
- **25 נקודות** הן בערך 1.2 ימי הפרעה בשנה. מעבר tier מדווח תמיד, כי זה מה שהאנליסט רואה בטבלה.
- **Digest:** הודעה אחת עם 17 hubs נקראת. 17 הודעות נפרדות מקבלות mute.
- **Outlook ריק נשמר אבל לא נשלח.** הודעה חודשית של "אין מה לדווח" מלמדת אנשים להתעלם מהערוץ.
- **ה-caveats עוברים עם ההתראה:** "wind likely overstated" ל-hubs חופיים (אוקלנד, וירג'יניה ביץ'), ו-"Historical averages, not a forecast".

**דוגמה אמיתית (ינואר 2027):** 17 hubs, ובראשם Boston (index 964, very high, 3.90 ימים צפויים, 18 אירועי עבר) ו-Chicago (799).

## 2. Slack ו-webhook
- **Slack:** צ'אט ארגוני עם ערוצים. מקובל שמערכות שולחות לערוצים הודעות אוטומטיות.
- **Incoming Webhook:** כתובת URL סודית שמחוברת לערוץ. כל `POST` אליה עם `{"text": "..."}` מתפרסם בערוץ. לא צריך SDK או OAuth.
- **ה-payload שלנו:** `text` (מה ש-Slack מציג), `idempotency_key` (ה-dedup key), ו-`alert` (הנתונים המובנים).
- **כל מקבל עובד:** Teams, מערכת tickets, webhook.site.
- **`ALERT_WEBHOOK_URL`:** כשהוא לא מוגדר, ההתראה נשמרת בסטטוס `stored` ומוצגת רק בדף וב-API.
- **כתובת ה-webhook היא סוד.** היא נשמרת רק ב-`.env` או ב-dashboard של Render, ואף פעם לא ב-git.

## 3. מתי בודקים אם הציון השתנה (הכי חשוב להבין)

**הבדיקה צמודה לרגע שבו ה-run החדש הופך לפעיל, באותה טרנזקציה.** אין polling שבודק אם משהו השתנה.

שלושה מסלולים, וכולם מגיעים ל-`store.save_run()`:
```
① python -m app.ingest           → score_after_ingest() → ensure_current() ─┐
② python -m app.scoring.store --new → new_run()                          ─┼→ save_run()
③ עליית שרת → load_results() → ensure_current()                          ─┘
   (רק אם ה-hash של disruption.yaml או ה-fingerprint של הנתונים השתנה)
```
- ingestion שנכשל **לא** יוצר run, כי נתונים חלקיים לא צריכים להפוך לציונים הפעילים.
- run זהה (אותם חוקים ואותם נתונים) **לא** יוצר התראה.

**בתוך `save_run` (`app/scoring/store.py`):**
```
חישוב הניקוד (1.1 שניות, מחוץ לנעילה)
BEGIN IMMEDIATE                         ← נעילת כתיבה
  בדיקה חוזרת: run זהה כבר פעיל? → מחזירים אותו (בלי run כפול ובלי התראה כפולה)
  previous = ה-run הפעיל (נקרא בתוך הנעילה)
  INSERT של ה-run החדש
  ישן → superseded, חדש → active
  record_change_alert(conn, previous, new)   ★ השוואה ב-SQL: JOIN בין שני ה-runs
COMMIT                                  ← ההפעלה וההתראה יחד, או לא בכלל
deliver_pending()                       ← שליחה מיידית (best effort)
```

**שלוש נקודות להדגיש:**
1. **מי שמפעיל את ה-run יוצר את ההתראה.** אם ה-ingestion רץ בלפטופ, תהליך ה-ingestion שולח. השרת קולט את ה-run החדש תוך **5 שניות**.
2. **ההשוואה היא שאילתת SQL** בין `hub_results` ו-`hazard_scores` של שני ה-runs. המנוע לא רץ שוב.
3. **ההתראה נכתבת באותה טרנזקציה של ההפעלה,** כך ש-run לא יכול להפוך לפעיל בלי ההתראה שלו, גם אם התהליך קורס.

## 4. התזמון של ה-outlook
```python
# app/main.py, _alerts_loop
check_outlook()     # ליצור את ה-outlook אם הגיע הזמן
deliver_pending()   # לשלוח מה שממתין, כולל ניסיונות חוזרים
sleep(60)           # alerts_check_interval_seconds
```
- **איזה חודש:** החודש של "היום + 7 ימים". ב-24 בנובמבר זה 1 בדצמבר, ולכן נוצר ה-outlook של דצמבר.
- **ההתראה נוצרת פעם אחת.** כל סבב אחר נתקל במפתח הקיים ולא עושה כלום.
- **Catch-up:** אם השרת היה כבוי במועד, ההתראה נוצרת בעלייה הבאה עם הסימון "sent late". הבדיקה היא "האם עבר המועד?", ולא "האם עכשיו השעה X?".
- **`asyncio.to_thread`:** webhook איטי לא תוקע את ה-event loop של ה-API.
- **טריגר חיצוני:** `POST /alerts/check` הוא אידמפוטנטי ומוגן ב-`X-Alerts-Token` כש-`ALERTS_TOKEN` מוגדר.

**"60 שניות זה לא בזבוז?"**
- מדדתי: כ-**10ms** לסבב, כלומר בערך **14 שניות CPU ביום**, בלי רשת.
- הקצב נקבע בגלל **השליחה החוזרת**, שצריכה לרוץ כל דקה. ה-outlook רץ באותה לולאה כי הוא זול ואידמפוטנטי.
- **מה הייתי משפר:** שני קצבים (שעה ל-outlook, דקה לשליחה), ובדיקת קיום של המפתח **לפני** חישוב ה-digest. היום ה-digest מחושב בכל סבב ונזרק. בנוסף, כל סבב כולל `INSERT OR IGNORE`, שלוקח לרגע את נעילת הכתיבה.

⚠️ **אי-התאמה בתיעוד:** ב-README וב-`DESIGN_DECISIONS.md` כתוב "hourly check", אבל בקוד הסבב הוא **כל 60 שניות**.

## 5. הבטחות ה-concurrency

| הבטחה | איך היא מושגת |
|---|---|
| **יצירה exactly-once** | `dedup_key TEXT UNIQUE` ו-`INSERT OR IGNORE`. ה-DB מחליט מי יצר, ו-`rowcount` מספר לנו אם זה היינו אנחנו |
| **שום התראה לא הולכת לאיבוד** | **Transactional outbox:** התראה נשמרת כ-`pending` באותה טרנזקציה עם הסיבה שלה, והשליחה היא שלב נפרד |
| **אין שליחה כפולה בין senders** | **Claim:** `UPDATE ... WHERE alert_id = (SELECT ... LIMIT 1) RETURNING *`, statement אחד שמחזיק את נעילת הכתיבה ומציב `lease_until` |
| **התאוששות מקריסה** | ה-lease (**120 שניות**) פג, ו-sender אחר לוקח את ההתראה |
| **אין ניסיונות אינסופיים** | אחרי **5** ניסיונות הסטטוס הופך ל-`failed`, והשגיאה נשמרת ב-`delivery_error` |
| **שליחה at-least-once** | מעל HTTP אי אפשר exactly-once (ייתכן שה-POST הגיע והתשובה אבדה). לכן נשלח `idempotency_key`, ו-at-least-once ועוד מקבל אידמפוטנטי נותנים effectively-once |
| **אין run כפול בעליות מקבילות** | `BEGIN IMMEDIATE` ובדיקה חוזרת בתוך הנעילה |
| **ה-"previous" תמיד נכון** | הוא נקרא בתוך הנעילה, ולכן ההפעלות טוריות (1→2→3) |

**מחזור החיים של התראה:**
```
pending ──claim + lease 120s──► POST ──ok──► delivered
   ▲                             │
   └──── נכשל או קרס (lease פג) ──┘   ... 5 ניסיונות ──► failed
stored = לתצוגה בלבד (אין webhook, או outlook ריק)
```

**כל race שוחזר קודם ב-stress test** (8 threads, ושרתים שעולים במקביל), ורק אז תוקן.

**המקבילות ב-Postgres:** `ON CONFLICT DO NOTHING` ליצירה, `FOR UPDATE SKIP LOCKED` ל-claim, ו-advisory lock להפעלת run.

## 6. הפרדת מדיניות מחוקים
`config/alerts.yaml` **נפרד** מ-`config/disruption.yaml`. שינוי סף של התראה הוא שינוי מדיניות, ולא שינוי בציונים. אם הספים היו באותו קובץ, ה-hash היה משתנה, נוצר scoring run חדש, ונשלחת התראת "שינוי" כשבפועל לא השתנה כלום.

## 7. למה התזמון בתוך השרת ולא ב-scheduler חיצוני
זו הייתה החלטה מודעת, שמתועדת ב-`PLAN.md` סעיף 2.9 יחד עם המגבלה.
1. **ה-SQLite הוא קובץ בתוך ה-container.** scheduler חיצוני רץ ב-container אחר ולא יכול לגשת לקובץ, כך שהוא יכול רק לקרוא לשרת ב-HTTP. כלומר רק השעון היה עובר החוצה, לא העבודה.
2. **את לולאת השליחה החוזרת צריך ממילא כל דקה.** scheduler חיצוני היה רק מוסיף רכיב.
3. **זה עובד מיד אחרי clone,** בלי הגדרות. בלי זה, בודק המטלה לא היה מקבל התראות מתוזמנות.
4. **בונוס בתוך 24 שעות:** הלולאה היא כ-10 שורות, בלי תשתית נוספת.
5. **ב-Render החינמי זה לא היה עוזר,** כי הבעיה שם היא ה-DB הזמני.

**מה כן הוכן:** `POST /alerts/check`, אידמפוטנטי ומוגן. cron חיצוני יכול לרוץ **במקביל** ללולאה בלי כפילויות.

**פרודקשן:** Postgres משותף, API replicas שמטפלים רק ב-HTTP, worker לשליחה מה-outbox, ו-scheduler מנוהל (Cloud Scheduler, EventBridge או k8s CronJob) עם dead man's switch לניטור.

## 8. מגבלות שכדאי להעלות ביוזמתך
- **Render החינמי: ה-DB נמחק בכל restart.** לכן:
  - **התראת score change לא תופיע אחרי deploy**, כי אין run קודם (`previous = None`).
  - **ה-dedup לא שורד restart.** אם מוגדר webhook, ה-outlook עלול להישלח שוב אחרי שהשירות מתעורר משינה.
  - **הניסוח לראיון:** "ה-dedup וההשוואה בין runs עמידים בדיוק כמו ה-DB. בפרודקשן צריך DB קבוע."
- **ה-Incoming Webhook של Slack לא מסנן לפי `idempotency_key`.** במקרה נדיר תופיע כפילות.
- **אין תחזית.** הכול מבוסס על ממוצעים היסטוריים. הצעד הבא הוא NWS (`api.weather.gov`) להתראות בנוסח "סערה מגיעה השבוע".
- **הלולאה רצה בכל replica.** אין כפילות בתוצאה, אבל העבודה כפולה.
- **ה-outlook מחושב בכל סבב** ונזרק כשהמפתח כבר קיים.

## 11. שאלות ותשובות קצרות
- **Slack לא זמין?** ההתראה נשארת `pending`, ויש ניסיון חוזר כל 60 שניות. ה-lease מונע ניסיונות מקבילים, אחרי 5 כשלונות הסטטוס הוא `failed`, ושום דבר לא נחסם.
- **למה לא `threading.Lock`?** הוא מגן רק בתוך תהליך אחד. ה-races היו בין תהליכים, ורק ה-DB משותף לכולם.
- **`BEGIN` מול `BEGIN IMMEDIATE`?** `BEGIN` לוקח נעילה רק בכתיבה הראשונה, ולכן שתי טרנזקציות יכולות לקרוא מצב ישן. `IMMEDIATE` נועל כבר בהתחלה.
- **למה lease של 120 שניות?** ארוך מ-POST עם 3 retries (10 עד 20 שניות במקרה הגרוע), וקצר מספיק כדי שהתראה של sender שקרס תצא תוך כמה דקות.
- **אפשר exactly-once delivery?** לא מעל HTTP בלי שיתוף פעולה של המקבל. לכן at-least-once עם idempotency key.
- **למה התראה באותה טרנזקציה של ההפעלה?** אם הייתה נכתבת אחרי ה-commit, קריסה ברגע הזה הייתה משאירה run פעיל בלי התראה.
- **איך יודעים שה-job רץ?** dead man's switch (Healthchecks.io או Cronitor), או התראה כשאין outlook לחודש הבא 3 ימים לפני תחילתו.
- **למה `alerts.yaml` נפרד?** כדי ששינוי מדיניות לא ייצור run חדש והתראת "שינוי" שבה לא השתנה כלום.
